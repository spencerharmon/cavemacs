* Postmortem: R1 + R2 (interactive-only regressions)

** R1 — UI appeared upside-down

Symptom: in interactive Emacs the buffer showed the banner at the top
of the window and the prompt scrolled off the bottom.  Comparable
interfaces (caveman's TUI, browser chat, every Emacs comint-derived
shell) put the prompt at the bottom of the visible window with the
most recent message just above it.

Root cause: the buffer's *content* order was already correct (oldest
turn first, newest turn just above the separator+prompt).  But the
window's default scroll position was BOB, so the prompt was off the
bottom of the visible area.  The interactive tests caught it, the
batch tests (which never displayed the buffer in a window) did not.

Fix: in `cavemacs-shell-mode' set the standard comint scroll settings
(`scroll-conservatively' 101, `scroll-margin' 0).  And in
`cavemacs-render--at-output' detect when point is at point-max
*before* a render insert and advance it (plus every live window's
window-point) to the new point-max *after* the insert.  Result:
typing input area stays pinned to the bottom of the window; new
turns render just above it; older turns scroll up out of view.

** R2 — RET stopped sending after the first prompt

Symptom: after the first response rendered, hitting RET in the input
area inserted a literal newline instead of submitting.  Could only
send the very first prompt.

Root cause: `save-excursion' in `cavemacs-render--at-output' restores
point by its *numeric position*, not by trailing-the-tail.  When the
user's point was at point-max during a streaming render, save-excursion
snapshotted the numeric position; the renderer then inserted text
*before* that position; after restore, point was now in the middle of
the rendered output, *not* at point-max.  `(eobp)' returned nil, and
`cavemacs-shell-send-or-newline' fell through to its `(newline)' branch.

Why batch tests missed it: every batch test explicitly did
`(goto-char (point-max))' before each `cavemacs-shell-send', which
papered over the issue.  The stricter regression test added with the
fix uses `(call-interactively #'cavemacs-shell-send-or-newline)' and
asserts `(eobp)' *without* a manual goto-char first.

Fix: same as R1 (advance point + every window-point to the new
point-max after each render insert, when the user was at the bottom).

* Bugfix: C-a moves point into read-only prompt

** Symptom

Pressing =C-a= (=beginning-of-line= / =move-beginning-of-line=) in
the shell input area moves point to column 0, inside the read-only
prompt prefix (the => = character and separator).  The user can't
type there, but the cursor position is confusing and breaks
expectations — =C-a= should land at the first editable column.

** Fix

Bind =C-a= (and possibly =home=) in =cavemacs-shell-mode-map= to a
command that moves point to =cavemacs-shell--input-start-marker=
instead of =(line-beginning-position)=.  Respect =shift-select-mode=
so =C-S-a= still sets mark correctly.

* M11 — Collapsible thinking text and tool-call blocks

** Goal

Thinking text and tool-call output can be verbose, dominating the
buffer and pushing conversation content off-screen.  Render these
blocks collapsed by default with a clickable/keybound toggle to
expand or collapse them in place.

** Requirements

- Thinking blocks render collapsed (single summary line, e.g.
  =▶ Thinking (42 lines)=) by default.
- Tool-call blocks render collapsed (e.g. =▶ tool: read file.el=)
  by default.
- =TAB= or =RET= on a collapsed header expands the full content
  inline; same key collapses it again.
- Mouse click on the header also toggles.
- A command / custom variable to toggle *all* blocks in the buffer
  (expand-all / collapse-all).
- Expanded state is buffer-local and non-persistent (restarting
  session resets to collapsed).

** Implementation sketch

- Use overlays with =display= or =invisible= property on the body
  region; keep the header line always visible.
- Store expand/collapse state as an overlay property.
- Add a keymap on the header overlay (=keymap= property) for
  =TAB= / =RET= / mouse-1 toggles.
- Hook into =cavemacs-render.el= where thinking and tool-call
  events are inserted.

** Related files

- =cavemacs-render.el= (insertion of thinking / tool-call blocks)
- =cavemacs-shell.el= (buffer keymap coordination)

* M10 — Slash command dispatch + in-prompt autocomplete

** Problem (discovered post-v0.1.0)

Typing =/help= or =/model= in the input area sent the literal string
as a `prompt' RPC.  The LLM dutifully answered the question in plain
English ("Here are the tools and functionality you can use..."), but
nothing happened mechanically: the model didn't change, the context
didn't compact, the session didn't reset.

Root cause: caveman's built-in slash commands (=/help=, =/model=,
=/compact=, =/cost=, =/clear=, ~30 of them) are implemented in
caveman's *interactive TUI input handler*, not in the agent loop.
In =--mode rpc=, that handler is bypassed entirely.  Sending =/model=
as a `prompt' is treated as user text, not a command.

User-defined slash commands (extensions, prompt templates, skills)
do work over RPC: caveman's `prompt' handler invokes them before
forwarding to the LLM.  But those have to be installed by the user
first; the built-ins were the missing piece.

** Design

Two pieces:

*** Local dispatch

A small built-in registry in =cavemacs-commands.el= maps the most
important caveman built-ins to their direct RPC equivalents:

| Slash    | RPC verb              |
|----------+-----------------------|
| /help    | (local, prints help)  |
| /model   | get_available_models + set_model |
| /thinking | set_thinking_level   |
| /compact  | compact              |
| /new, /clear | new_session       |
| /name    | set_session_name      |
| /session | get_session_stats     |
| /export  | export_html           |
| /copy    | get_last_assistant_text |
| /bash    | bash                  |
| /abort   | abort                 |

`cavemacs-shell-send' calls `cavemacs-commands-dispatch' before
sending; if the input parses as a known built-in, the handler runs
and the input is *not* forwarded to the LLM.  Otherwise (regular
prompts and user-defined slash commands alike), the text goes
through to caveman's `prompt' RPC unchanged.

*** In-prompt autocomplete via completion-at-point

Adds `cavemacs-commands-capf' to the buffer's CAPF list.  Active
when the input area starts with =/= and point is on the first word.
Offers both built-in commands and user-defined commands (the latter
fetched lazily via the `get_commands' RPC, cached for 5 seconds per
buffer to avoid round-trip storms during typing).

Works automatically with the default Emacs completion UI, Corfu,
Company, and any other CAPF consumer.  =TAB= is bound to
`completion-at-point' in cavemacs-shell-mode for users without a
popup completion frontend.

** Exit criteria (met)

- =/help= in the input area shows the built-in command list inline.
- =/model RET= opens a completing-read picker and switches models.
- =/compact RET= triggers a real context compaction.
- Typing =/= in an otherwise-empty input area + TAB shows
  completion candidates with descriptions.
- User-defined commands from =get_commands= appear in the
  completion list alongside built-ins (when an extension or prompt
  template is installed).
- Regression tests cover the parser, dispatch decision, and CAPF
  shape.

* Overview

cavemacs is an Emacs front-end ("shell") for the [[https://github.com/JuliusBrussee/caveman-code][caveman-code]]
terminal coding agent. It wraps the =caveman= binary as an external
process and surfaces its agent loop inside an Emacs buffer with
streaming output, markdown rendering, tool call approvals, and
per-project session persistence. It is designed to compose cleanly
with the rest of the Caveman ecosystem:

- *caveman-code* — the agent runtime cavemacs drives (source of truth).
- *cavekit* — the spec-driven workflow (=/ck:spec=, =/ck:build=,
  =/ck:check=) lives as slash commands inside the caveman session;
  cavemacs surfaces them in completion + a transient menu.
- *cavemem* — persistent memory backend; cavemacs does not talk to it
  directly (caveman-code already does), but exposes =/memory= commands
  and a viewer-launch helper.

** Target environment

- Emacs 30.2+ (per user).
- =caveman= installed on =PATH= (npm: =@juliusbrussee/caveman-code=).
- Optional: =cavemem= installed; viewer at http://127.0.0.1:37777.
- Optional: =cavekit= plugin installed in the project (=SPEC.md=,
  =.claude/= or =.cave/= dirs).

** Protocol decision (key finding from research)

caveman-code exposes four programmatic surfaces (see
=caveman-code/docs/api.md=):

1. =caveman --mode rpc= — *JSON-RPC over stdin/stdout, JSONL framed.*
   Methods: =session.create=, =session.prompt=, =session.events=
   (server-streamed), =session.tool.allow=, =session.compact=,
   =session.fork=, =session.close=.
2. =caveman --mode json -p "…"= — one-shot, stable event stream
   (=session.start=, =tool.call=, =tool.result=, =token=, =session.end=).
3. =caveman serve= daemon (HTTP + WebSocket) + =@juliusbrussee/caveman-sdk=.
4. In-process Node SDK (not usable from Emacs).

*Decision:* cavemacs targets surface #1 (=--mode rpc=) as the primary
transport, with surface #2 as a fallback for one-shot =M-x= helpers.
The daemon (#3) is a *Phase 4 stretch* — useful for multi-client /
SSH-survival but not required for v1.

[CORRECTED during M0 — the docs misrepresent the protocol]

The actual =--mode rpc= protocol verified against
=caveman-code/packages/coding-agent/src/modes/rpc/= is *NOT* JSON-RPC
2.0.  It is a custom envelope:

  Commands  : ={"id"?: <str>, "type": <verb>, ...}=
  Responses : ={"id"?, "type":"response", "command":<verb>, "success":<bool>,
                "data"?: ..., "error"?: ...}=
  Events    : ={"type": <event-type>, ...}=  (no id, no envelope)
  UI reqs   : ={"type":"extension_ui_request", "id":<uuid>, "method": ...}=
  UI replies: ={"type":"extension_ui_response", "id":<echo>, ...}=

Verbs are =prompt= (not =session.prompt=), =new_session= (not
=session.create=), =abort=, =fork=, =compact=, =get_state=,
=get_messages=, =get_commands=, =set_model=, =cycle_model=,
=get_available_models=, =set_thinking_level=, =cycle_thinking_level=,
=switch_session=, =bash=, etc.

There is *no per-command sessionId*.  The running process *is* the
session.  =new_session= resets in place; =switch_session= loads a
different on-disk session file.

Tool approvals do not have a dedicated event type — they flow through
=extension_ui_request= with =method:"confirm"=.

This means the M3 "tool approval UI" design pivoted: rather than a
dedicated approval channel, cavemacs registers a *UI handler* that
claims =extension_ui_request= confirms.  The =-protocol-version=v1=
flag advertised in docs does not exist in this version of caveman.

** M1 — Package skeleton & RPC core :foundation:
*Goal:* a working but UI-poor =M-x cavemacs= that streams to a buffer.

[CORRECTED] We did *not* use =shell-maker= after all.  After M0
exposed the full event vocabulary, it became clear that:

- Caveman streams asynchronous events outside the prompt/response
  rhythm (=tool_execution_*=, =extension_ui_request=, =compaction_*=).
- Tool approvals need inline interactive blocks at arbitrary buffer
  positions, not at the prompt position.
- Multi-part assistant messages (text + thinking + tool_use
  interleaved) want region-based replacement, not the append-only
  model =shell-maker= assumes.

cavemacs therefore defines its own =cavemacs-shell-mode= derived from
=fundamental-mode=, with a dedicated read-only output area above a
prompt marker and a multi-line input area below.  This kept the
dependency surface small (only =markdown-mode= and =transient=) and
gave full control over overlay-based streaming updates.

*Package layout* (multi-file, one module per concern):

- =cavemacs.el= — entry points, autoloads, top-level customs, version.
- =cavemacs-rpc.el= — process management, JSONL framing, request/
  response correlation, event dispatch.
- =cavemacs-shell.el= — =shell-maker= integration, buffer setup,
  prompt, keymap.
- =cavemacs-render.el= — streaming text insertion, markdown rendering
  (defer to =markdown-mode= fontification for blocks), tool-call
  block formatting.
- =cavemacs-tools.el= — tool-call permission UI (approve/deny/always).
- =cavemacs-session.el= — session metadata, resume, fork, list.
- =cavemacs-project.el= — git-root / =project.el= detection, per-repo
  session directory (=~/.cave/agent/sessions/<cwd-hash>/= mirrors
  caveman's own layout).
- =cavemacs-commands.el= — slash command discovery + completion.
- =cavemacs-cavekit.el= — cavekit transient menu (=/ck:spec= etc.).
- =cavemacs-cavemem.el= — =/memory= helpers + viewer launcher.
- =cavemacs-mock.el= — replay fixture transcripts; used by tests.

*Dependencies* (declare in =Package-Requires=):
- =emacs "30.1"=
- =shell-maker "0.78.1"= (or current)
- =markdown-mode= (for fontification of streamed blocks)
- =transient= (built-in; for cavekit / command menus)
- =project= (built-in)

cavemacs implements caveman's RPC protocol directly, with no
intermediate transport library.  The protocol layer is bespoke to
this project.

*RPC core requirements:*
- One =caveman --mode rpc --protocol-version=v1= subprocess per shell
  buffer; lifecycle tied to buffer.
- JSONL line-oriented reader with partial-line buffering (newline-
  delimited; never assume a single read = single message).
- Request table keyed by =id=; promise-style callbacks (cl-style with
  a small =cavemacs-rpc--pending= hash table).
- Event sink: dispatch on =method= / =type= to per-buffer handlers.
- Graceful shutdown on buffer kill (=session.close= then
  =delete-process=).

*Exit criteria:* =M-x cavemacs= opens a shell, =hello= round-trips,
tokens stream into the buffer in real time, =C-c C-c= cancels the
in-flight prompt.

** M2 — Rendering & markdown :ui:
*Goal:* readable, well-formatted streamed output.

- Streaming insertion that preserves point if user is reading
  scrollback; jump-to-bottom otherwise.
- Per-turn structure: user prompt, assistant response, optional tool-
  call sub-blocks, footer with token/cost from =session.end=.
- Markdown rendering strategy: accumulate the current assistant turn
  in an overlay-backed region; on each token delta, re-fontify the
  changed range using =markdown-mode='s font-lock keywords (cheaper
  than re-rendering). Code fences get =org-src=-style native
  fontification via =markdown-fontify-code-blocks-natively=.
- Caveman-mode terse output renders fine as markdown; no special case.
- Diff rendering: caveman emits unified diffs in tool results; render
  in a collapsible block using =diff-mode= fontification.

*Exit criteria:* a multi-turn session with code, diffs, and tool calls
renders cleanly.

** M3 — Tool-call approvals :ui:safety:
*Goal:* full permission UI parity with caveman's TUI.

caveman emits a permission-prompt event when a tool needs approval
(unless =--autopilot= is on). cavemacs must:

- Render the pending tool call inline in the buffer with the proposed
  args (file path, command, diff preview).
- Offer keyed actions: =a= approve once, =A= approve & remember (sets
  =session.tool.allow= with persistence flag), =d= deny, =e= edit args
  before approving (where caveman supports it — confirm in protocol),
  =q= dismiss / cancel turn.
- Implement as a =transient= prompt anchored to the tool-call block,
  with a fallback =read-char-choice= for non-transient users.
- Respect a customizable =cavemacs-autopilot= toggle that passes
  =--autopilot= at process start (mirrors caveman's flag exactly).

*Exit criteria:* an =Edit= tool call on a real file shows a diff,
prompts, and applies on approval.

** M4 — Session persistence & multi-session UI :sessions:
*Goal:* multiple concurrent buffers + a project-scoped session
browser.

- Each shell buffer = one caveman session = one =caveman --mode rpc=
  subprocess. Buffers named =*cavemacs: <project> · <short-id>*=.
- Persistence is *delegated to caveman* — it already writes JSONL to
  =~/.cave/agent/sessions/<cwd>/=. cavemacs reads that directory to
  enumerate.
- =M-x cavemacs= behaviour:
  - If no session in current project's repo → start a new one.
  - If exactly one live buffer for this project → pop to it.
  - If sessions exist (live or on disk) → open the session browser.
- =cavemacs-session-browser= (Phase 4 of M4):
  - Scoped to current git-repo / =project-current= root by default;
    =g a= toggles "all projects".
  - Columns: timestamp, model, turn count, last-user-prompt-preview,
    cost. Backed by =tabulated-list-mode=.
  - Actions: =RET= resume (continues subprocess against the on-disk
    session id via =session.create= with a =resumeFrom= param —
    confirm method name from RPC), =f= fork (=session.fork=), =d=
    delete on disk, =c= compact (=session.compact=).
- Continue-most-recent shortcut: =M-x cavemacs-continue= (=caveman -c=
  semantics).

*Exit criteria:* user can have three projects' sessions open in three
buffers simultaneously, kill Emacs, reopen, and resume each from the
browser.

** M5 — Slash commands, cavekit & cavemem integration :compat:
*Goal:* feature parity with caveman's TUI command surface, plus
ecosystem niceties.

- *Slash command completion.* caveman's =/= triggers built-in +
  user-defined commands (=~/.cave/commands/*.md= and =.cave/commands/
  *.md=). cavemacs:
  - Detects =/= at the start of input and pops a =completing-read=
    (or in-buffer Company/Corfu via =completion-at-point-functions=)
    with descriptions parsed from the markdown frontmatter.
  - Sources: built-ins discovered by asking caveman over RPC if it
    exposes a =commands.list= method (verify; otherwise scan the
    directories ourselves — schema is documented in
    =docs/reference/slash-commands.md=).
- *cavekit transient.* =M-x cavemacs-cavekit= opens a =transient=
  with =/ck:spec=, =/ck:build=, =/ck:check= (v4) and the v3.1.0
  command set if =SPEC.md= absent but =context/kits/= present. Each
  entry just sends the corresponding slash command into the active
  session.
- *cavemem integration.*
  - =M-x cavemacs-memory-search= → prompts for a query, sends
    =/memory search= in current session OR shells out to =cavemem
    search= directly for a non-session lookup (configurable).
  - =M-x cavemacs-memory-viewer= → =browse-url
    "http://127.0.0.1:37777"=, auto-starting the worker via =cavemem
    start= if not running.
  - =M-x cavemacs-memory-sync-from-claude= → wraps =/memory sync
    --from claude=.
- *MCP visibility (read-only).* Parse =.mcp.json= in project root +
  =~/.cave/settings.json=; show configured servers in a header-line
  segment. No management UI in v1.

*Exit criteria:* a cavekit-using project can run its full
spec → build → check loop from inside Emacs without touching the
terminal.

* Non-goals (v1)

- No reimplementation of caveman-mode compression in Elisp — caveman
  does it.
- No native MCP client in Emacs — caveman is the MCP host.
- No memory storage in Emacs — cavemem owns that.
- No support for arbitrary LLM providers outside what caveman already
  configures. cavemacs is a *front-end*, not an alternative agent.
- No Windows-specific work in v1 (matches caveman's own daemon
  roadmap).
